# Проверка доверия устройств и аккаунтов Matrix

Обновлено 04.10.2026. **Доверие к аккаунту iPad подтверждено нативным SDK на Tecno — по результату, сообщённому владельцем.** После подготовки D5 и инструкции повторно прочитать статус без нового сравнения владелец ответил: «подтверждён». Ранее он подтвердил сессию Tecno через Компьютер. Этапы сравнения и итогового доверия теперь пройдены; повторять их сейчас не требуется. Агент самостоятельно устройствами не управлял. Точное время получения подписи и причина прежней задержки не установлены; успех не доказывает ранее рассматривавшуюся гипотезу об отсутствии приватного ключа подписания.

В следующем сообщении 04.10.2026 владелец подтвердил: **после полного закрытия и повторного открытия приложения на Tecno доверие к аккаунту iPad сохраняется**. Результат зафиксирован со слов владельца; точный способ завершения процесса не уточнялся. Это проверка повторного открытия с сохранёнными данными приложения, а не переустановки или восстановления ключей.

Названия устройств, согласованные с владельцем:

- **Tecno** — прототип, первый Matrix-аккаунт.
- **iPad** — Element X, второй Matrix-аккаунт. В дальнейших инструкциях называем его iPad.
- **Компьютер** — Element Web с тем же первым аккаунтом, что на Tecno.

При запуске открывается вкладка «Устройства»: подтверждение iPad и проверка статуса. Прежние тесты сообщений, входа, шифрования, повторного подтверждения Tecno через Компьютер и отдельный экран SDK находятся в «Диагностике». Переключение вкладки меняет search-параметр Expo Router в том же экране, сохраняя клиент и сессию; во время операции переключение заблокировано. Статус и сравнение остаются вверху.

## Справочный сценарий проверки статуса с D5

Этот сценарий уже завершился подтверждением аккаунта iPad по сообщению владельца. Инструкции ниже сохранены для последующих проверок.

1. На Tecno выполните Reload и дождитесь автовхода. Оставьте Element на Компьютере и Element X на iPad открытыми.
2. Сначала нажмите «Проверить статус доверия». Теперь при неподтверждённом статусе приложение оставляет sync включённым до 75 секунд и повторно читает состояние из SDK. Новое сравнение не отправляется. Это даёт время получить отложенные подписи, но само по себе не гарантирует их появления.
3. Если iPad подтверждён, повторное сравнение не требуется. Если он всё ещё ожидает подтверждения, сообщите итоговые статусы. Продолжать многократно одинаковое сравнение без выяснения причины не нужно.
4. При следующем согласованном сравнении эмодзи сохраняется порядок D4: Tecno отправляет запрос, SAS запускает Element X. После native Done эмодзи скрываются, а SDK продолжает получение событий до 75 секунд. Успех появляется только при настоящем подтверждении всех требуемых ключей.
5. Если время обновления закончилось без доверия, показываются отдельные статусы и промежуточный результат, а не ошибка сравнения. «Последнее сравнение · D5» содержит безопасный снимок этих статусов. Кнопка чтения статуса сохраняет этот журнал; он относится к предыдущему сравнению. Отмена ожидания по-прежнему доступна. Журнал хранится в памяти экрана, поэтому сохраните его перед Reload.

Владелец подтвердил сессию Tecno через Компьютер, доверие SDK на Tecno к аккаунту iPad и сохранение этого доверия после закрытия и повторного открытия приложения. Разделы подготовки первого аккаунта и подтверждения сессии Tecno оставлены как справка для повторной настройки. Ранее отдельно проверялись сохранённый вход и расшифровка прежних сообщений.

## Почему изменено ожидание в D5

В точном SHA установленного Rust SDK `1c44fb6` SAS Done, подпись identity и повторное получение этой подписи — отдельные этапы. [Отправка очереди E2EE](https://github.com/matrix-org/matrix-rust-sdk/blob/1c44fb6/crates/matrix-sdk/src/sliding_sync/mod.rs#L555) запускается вместе с очередным sync; [стандартный long poll равен 30 секундам](https://github.com/matrix-org/matrix-rust-sdk/blob/1c44fb6/crates/matrix-sdk/src/sliding_sync/builder.rs#L54). Прежнее окно в 10 секунд могло закончиться раньше следующего цикла. D5 оставляет sync до 75 секунд с ранним завершением при настоящем доверии и немедленным прекращением ожидания при отмене.

`userIdentity(userId, true)` читает существующую identity из crypto store; `true` разрешает сетевой запрос только при отсутствии локальной identity. Повторное чтение этого метода не равнозначно принудительному обновлению ключей с сервера. Отдельное чтение статуса раньше запускало и сразу останавливало sync; теперь оно также ожидает изменения при неподтверждённом результате.

В [реализации SAS](https://github.com/matrix-org/matrix-rust-sdk/blob/1c44fb6/crates/matrix-sdk-crypto/src/verification/mod.rs#L547) отсутствие приватного user-signing key может оставить сравнение завершённым без подписи чужого аккаунта. Это возможная причина, **не подтверждённый диагноз данного устройства**. Установленный JS/FFI API не предоставляет `crossSigningStatus` или принудительный `request_user_identity`. D5 не экспортирует секреты, не открывает вторую crypto store, не устанавливает доверие вручную и не сбрасывает ключи. Если ожидание не поможет, потребуется отдельная проверка доступности ключа подписания и серверной подписи, а не ещё одно увеличение тайм-аута.

Диагностика D5 сохраняет только итоговые флаги устройства, собственного и второго аккаунтов, этапы и время. Полный TrustStatus с идентификаторами остаётся только на экране результата. При изменении ранее подтверждённых ключей по-прежнему возвращается ошибка; pending никогда не считается успешной проверкой доверия. После valid Done + approve native cancel больше не вызывается, включая отмену ожидания обновления статуса.

## Что показала D3 и что изменено в D4

На присланных снимках видны принятие запроса на 5-й секунде, наша команда запуска SAS и два уведомления SDK о начале сравнения на 5-й и 6-й секундах. На 82-й секунде нажато «Всё совпало», approve вернулся без ошибки. На 123-й секунде пришёл `didCancel`, а на 124-й служебная остановка закончилась. Текст iPad сообщает об истечении ожидания, отклонении запроса или ошибке. Точный cancel code этот FFI не передаёт.

Два уведомления `didStartSasVerification` сами по себе не доказывают два независимых обмена: при локальном `startSasVerification` Rust также меняет состояние запроса на `Transitioned`, и оба пути уведомляют делегат. Однако исходники Element X показывают, что получатель запроса начинает SAS после завершения accept, а инициатор не запускает SAS из ready-callback. Наш прежний код начинал его и на стороне Tecno. В SDK локальный RPC и обработка incoming start могут менять активный SAS контроллера; исключение конкурирующего запуска — обоснованное изменение, но связь с конкретным тайм-аутом пока не доказана.

В D4 при проверке iPad Tecno отправляет только запрос подтверждения и ждёт входящий SAS, который нативный контроллер принимает сам. Повторные ready-callback не запускают дополнительный поток; таймерного резервного старта нет. Если iPad не начнёт сравнение, останется понятный статус ожидания и возможность отмены. Проверка собственной сессии через Компьютер сохраняет прежний порядок. Подтверждение совпадения человеком и все проверки доверия остаются обязательными.

## Что покажет диагностика D4

Журнал содержит только фиксированные названия этапов и время: запуск/состояние sync, подключение комнаты, запрос сравнения, получение эмодзи, возврат вызова подтверждения, завершение, отмену или ошибку SDK. Пароль, токены, ключи, адреса аккаунтов, комнаты, эмодзи и исходные тексты ошибок SDK в журнал не записываются. Хранится не более 40 последних этапов в памяти текущего экрана.

D3 добавляет остановку ожидания на Tecno, начало очистки, ожидание незавершённого approve, вызов и возврат native cancel, начало и окончание остановки sync. Теперь можно увидеть, на каком служебном вызове задержалась отмена.

D4 сохраняет эти этапы и добавляет «Ожидаем запуска сравнения на iPad». Для исходящего запроса iPad не должно быть нашей команды «Запущено сравнение». Количество уведомлений от SDK не используется как доказательство успеха или отказа. Стрелки в подписях заменены словами, поскольку на снимках Tecno они отображались неверно.

Экран прекращает ожидание через отдельный обработчик `AbortSignal`, не дожидаясь завершения native promise. Сам нативный процесс остаётся отслеживаемым: прежний клиент и живые объекты не уничтожаются до завершения cleanup, новая проверка не запускается поверх него. Поздний успех или ошибка не заменяют отменённый результат. После нормальной остановки кнопки снова доступны; при зависшем SDK показана инструкция полного перезапуска. Это не принудительное завершение Rust из JavaScript и не доказательство доставки отмены на iPad.

Отсоединение делегата перенесено на следующий проход очереди JavaScript: Rust вызывает делегат под read-lock, а `setDelegate` требует write-lock. Это избегает повторного входа из callback при очистке; наличие такого зависания именно на Tecno без нативных логов не установлено.

После «Всё совпало» запускается пробный `Client.getProfile()` собственного аккаунта через тот же нативный HTTP-клиент. По исходникам Rust SDK этот метод запрашивает профиль с сервера; результат профиля отбрасывается. Срок одного запроса — 12 секунд, следующий запрос выполняется через 30 секунд после предыдущего. Завершение/остановка проверки отменяет опрос. Операция только читает профиль и не меняет доверие.

Ответ сервера доказывает доступность именно этого запроса с Tecno в указанное время. Он не доказывает доставку MAC/done, исправность sync или соединение самого iPad. Ошибка профиля сама по себе также не доказывает обрыв сети и не может отменить успешный SAS. Нажатие кнопки, возврат approve и ответ сервера никогда не заменяют callback `didFinish` и проверку доверия в SDK. Нативный `didCancel` этой версии не передаёт причину отмены; интерфейс больше не приписывает её другому устройству.

## Подготовка первого аккаунта на компьютере

1. На Tecno выполните Reload в development client и дождитесь автовхода. Во вкладке «Устройства» показан полный адрес первого аккаунта.
2. На компьютере откройте [Element Web](https://app.element.io) и войдите именно в первый аккаунт с Tecno. Пароль вводите непосредственно в Element. Второй аккаунт в Element X оставьте.
3. Если это первая настройка шифрования аккаунта в Element, завершите её. Если аккаунт уже имеет настроенное подтверждение, используйте его существующие способы подтверждения. При предложении сбросить существующие ключи не выбирайте сброс в рамках этого сценария: сначала нужен текст этого конкретного запроса. Прототип не выполняет сброс.
4. Оставьте Element открытым на компьютере. На Tecno нажмите «Проверить статус доверия». Если SDK не нашёл собственную identity или другую подтверждённую сессию первого аккаунта, приложение показывает, чего не хватает. Повторите проверку после завершения входа и настройки в Element.

## Подтверждение сессии Tecno

1. Во вкладке «Диагностика» нажмите «Подтвердить Tecno через Компьютер».
2. В Element на компьютере примите запрос подтверждения этой сессии и выберите сравнение эмодзи. Держите оба приложения открытыми; ожидание ограничено пятью минутами.
3. На Tecno данные сравнения появляются вверху экрана. Сравните все семь эмодзи в указанном порядке с Element. Если SDK использует числа, сравните все три числа. Набор приходит от нативного протокола.
4. Если всё совпало, подтвердите совпадение на обоих экранах. На Tecno кнопки сравнения блокируются после первого ответа до окончания проверки. Если значения отличаются, нажмите «Не совпало».
5. Ожидается «Сессия Tecno подтверждена», а в статусе SDK — подтверждённое устройство и собственная identity. Нажатие «Всё совпало» само по себе не считается успехом.

Этот шаг подтверждает собственную сессию. Второй аккаунт им не подтверждается.

## Подтверждение аккаунта iPad

1. После успеха первого шага оставьте Element X открытым на iPad. Адрес его аккаунта берётся из сохранённой комнаты обмена.
2. На Tecno во вкладке «Устройства» нажмите «Подтвердить iPad».
3. В Element X на iPad примите запрос от аккаунта Tecno и сравните эмодзи или числа. Подтвердите совпадение на обоих экранах.
4. Ожидается «Аккаунт iPad подтверждён». Это подтверждение identity выбранного пользователя; список всех его устройств этим экраном не проверяется.

Если SDK уже считает второй аккаунт подтверждённым, новое сравнение не запускается: результат явно сообщает о существующем доверии. Отсутствие запроса в другом клиенте, отмена, несовпадение, неизвестное состояние или ошибка SDK не засчитываются как успех. Данные для сравнения и срок ожидания действуют только в текущей попытке.

## Реализация и условия успеха

- `NativeTrustTest` использует прежний клиент, crypto store и делегат сохранения сессии. Статус берётся из `Encryption.verificationState()`, `Encryption.userIdentity()`, `UserIdentity.isVerified()` и `hasVerificationViolation()`. Признак доверия не записывается в JSON SecureStore и не восстанавливается оттуда как доказательство.
- Для собственной сессии используются `Client.getSessionVerificationController()`, `requestDeviceVerification()`, затем SAS. Для выбранного другого пользователя используется `requestUserVerification(userId)`. Перед этим нужны подтверждённые собственное устройство и identity.
- Добавлена отсутствовавшая подписка на комнату проверки iPad. Rust SDK 0.18.0 отправляет запрос другого пользователя в `get_dm_room()` (или создаёт DM), тогда как собственная сессия подтверждается через to-device. Код получает фактическую DM через `Client.getDmRoom()`, вызывает `RoomListService.subscribeToRooms()`, сохраняет живой `Room.timeline()` и загружает участников. После запроса повторно обнаруживается возможная новая DM. Подписка и timeline живут до окончания операции. Готовность списка комнат сама по себе не заменяет эту подписку. Изменение кода не устранило реальный сбой владельца; считать подписку доказанной причиной нельзя.
- Данные приходят в `didReceiveVerificationData`: семь `SessionVerificationEmoji` или три числа. В интерфейс передаются только символы, описания и числа; обёртки эмодзи освобождаются. Случайные значения в JavaScript для сравнения не создаются.
- Одно явное решение пользователя вызывает `approveVerification()` или `declineVerification()`. Чужие входящие запросы не принимаются автоматически. Повторный ответ на тот же набор запрещён.
- Новый успех требует принятого сравнения, успешного вызова одобрения, `didFinish` от SDK, того же устройства и подтверждённого состояния ключей в SDK. Для другого пользователя также нужны совпавший адрес и его подтверждённая identity. Подписи могут появиться в хранилище чуть позже завершения SAS; sync остаётся активным ещё до десяти секунд проверки статуса.
- Обновление токена должно сохраниться без ошибок до результата. Старые контрольные события, пароль SQLite и сохранённый вход сохраняются. Отмена и ошибка не удаляют их. Получение событий останавливается, callback отключается; при неуспехе активный запрос отменяется с отдельным сроком ожидания.
- Ранее подтверждённые изменившиеся ключи не принимаются автоматически. Код не вызывает `resetIdentity`, `pin`, `withdrawVerification`, `recover` или `enableRecovery`. Обмен служебными ключами подтверждения при проверке собственной сессии выполняет сам SDK. Отдельный сценарий восстановления истории после удаления данных этим не реализован.
