# Rust в 2026 году для 4i7: современный стек, архитектура, инструменты и AI-разработка

## Главный вывод

По состоянию на **9 октября 2026 года** актуальный стабильный Rust — **1.99.0**, выпущенный 1 октября. Основная редакция языка для нового кода — **Rust 2024 Edition**. При этом наиболее значимый сдвиг последних двух лет для прикладной разработки произошёл не в Rust 1.99 как таковом, а с Rust 1.85, где Rust 2024 стал стабильным и появились, среди прочего, async closures; последующие версии в основном последовательно расширяли язык, стандартную библиотеку, Cargo и диагностику. citeturn7search0turn7search3turn1search0

Для **4i7 Rust подходит очень хорошо, но не как повод переписать весь backend**. Изученная архитектура проекта уже почти идеально подготовлена к постепенному внедрению Rust: domain отделён от Telegram/HTTP/ORM, боевая математика является чистой, детерминированной и версионированной, RNG формализован, replay является частью контракта, а состояние и транзакции отделены от вычислительного ядра. fileciteturn5file0L2-L2 fileciteturn6file0L2-L2

Самый рациональный путь выглядит так:

**Python/текущий backend оставить → перенести только `combat-core` в Rust → добиться полной parity с Python на golden/replay tests → подключить Rust в существующий Python через PyO3 → лишь затем решать, нужен ли вообще перенос HTTP/application/DB слоя на Axum + SQLx.**

Это гораздо безопаснее, чем начинать с нового Rust-backend.

Рекомендуемый долгосрочный стек для новых серверных проектов:

> **Rust 1.99 / Edition 2024 → Tokio → Axum → Tower / tower-http → SQLx + PostgreSQL → Serde → tracing → thiserror/anyhow → proptest + nextest + cargo-llvm-cov → cargo-audit + cargo-deny.**

Для 4i7 поверх этого я бы добавил собственный **детерминированный `combat-core`**, точные integer/rational value types, HMAC-SHA256 RNG, а на этапе миграции — **PyO3 + maturin**. WASM стоит рассматривать позже для replay/simulator/shared calculations, а не как основу Mini App.

## Современный Rust и что действительно стоит изучать

### Состояние языка в октябре 2026

Rust выпускается примерно шестинедельными циклами; в 2026 году вышли 1.93, 1.94, 1.95, 1.96, 1.97, 1.98 и 1.99, включая несколько patch-релизов. На 9 октября последней стабильной версией является **1.99.0**. Примечательно, что в 2026 году были и исправления miscompilation в 1.97.1 и 1.98.1, поэтому для production-проекта имеет смысл регулярно ставить patch-релизы, а не годами держаться за однажды выбранный compiler. citeturn7search3turn7search4turn7search9

Для нового проекта я бы зафиксировал:

```toml
[package]
edition = "2024"
rust-version = "1.99"
```

и `rust-toolchain.toml`, чтобы локальные разработчики, CI и агенты работали с одним toolchain.

Rust 2024 автоматически подразумевает Cargo dependency resolver v3, который учитывает `rust-version` зависимостей; в виртуальном workspace `resolver = "3"` лучше указывать явно. citeturn7search1turn7search6turn7search20

Для 4i7 особенно важны не модные отдельные синтаксические возможности, а пять фундаментальных свойств Rust:

**Enums + exhaustive matching.** Состояния `ROUND_OPEN`, `WAITING`, `RESOLVED`, `FINISHED`, результаты `KO`, `DOUBLE_KO_DRAW`, действия `ADVANCE/RETREAT/HOLD` естественно становятся типами, а не набором свободных строк.

**Newtypes.** Вместо повсеместного `i64` появляются разные `PlayerId`, `BattleId`, `Hp`, `BasisPoints`, `Distance`, `RoundNo`, `RulesetVersion`. Компилятор физически не даёт перепутать некоторые классы значений.

**Ownership.** Полезно здесь не ради «скорости», а потому что границы мутации становятся очевидными. Immutable round-start state, который уже используется в 4i7, очень естественно выражается в Rust.

**`Result` и typed errors.** Ошибка «нельзя выполнить действие в этой фазе боя» становится частью domain API, а не случайным exception.

**Чистое синхронное domain-ядро и async только снаружи.** Tokio нужен HTTP/DB/network слоям; формулы боя сами по себе не должны становиться `async`.

Последний принцип особенно совпадает с текущим 4i7: архитектурный документ проекта уже требует, чтобы domain не импортировал Telegram, FastAPI или ORM, а application layer координировал операции и короткие транзакции. fileciteturn5file0L2-L2

### Как сегодня писать Rust, а не «Rust из учебника»

Для backend-кода я бы закрепил следующие правила:

```rust
// Хорошая граница домена:
pub fn resolve_round(input: &RoundInput) -> Result<RoundResult, CombatError>

// Не такая:
pub async fn resolve_round(
    db: PgPool,
    telegram: TelegramClient,
    json: Value,
) -> anyhow::Result<Value>
```

`combat-core` не должен знать ни о Tokio, ни об Axum, ни о PostgreSQL. Он получает полностью сформированный `RoundInput`, валидирует его, вычисляет результат и возвращает `RoundResult`.

Ошибки domain лучше делать конкретными через `thiserror`; `anyhow` удобнее применять на верхних application/CLI/worker границах, где важнее контекст ошибки, чем программное сопоставление её вариантов. Актуальны `thiserror 2.0.21` и `anyhow 1.0.104`. citeturn17search0turn17search1

И ещё один важный принцип: **не использовать `Arc<Mutex<Everything>>` как архитектуру**. В серверной игре главным арбитром конкурентного доступа всё равно остаётся PostgreSQL-транзакция/CAS/version check. Rust устраняет целые классы memory/data-race ошибок внутри процесса, но не отменяет бизнес-гонки между двумя HTTP requests.

## Backend-экосистема и рекомендуемые crates

### Tokio как базовый runtime

Для такого backend я бы без особых сомнений выбирал **Tokio**. На момент исследования актуален Tokio **1.53.2**, выпущенный 3 октября 2026 года; ветка `1.53.x` объявлена LTS до сентября 2027 года. Tokio описывается как event-driven non-blocking I/O platform и является естественной основой для Axum, Tower и большого количества сетевого Rust-кода. citeturn15search1turn15search4turn15search7

Но важно понимать:

> **Tokio — инфраструктура, а не место для игровой математики.**

`resolve_round()`, расчёт дистанций, попаданий, HP, критов и outcome должны оставаться обычным синхронным Rust.

### Axum против Actix Web

На октябрь 2026 актуален **Axum 0.8.9**. Он построен поверх Tokio/Hyper/Tower и напрямую использует Tower middleware ecosystem; `tower-http` предоставляет tracing, compression, timeouts и другие HTTP middleware. citeturn8search18turn8search26turn10search23

Актуальный **Actix Web 4.15.0** также активно поддерживается; релиз вышел 21 августа 2026 года. Это совершенно рабочая production-альтернатива. citeturn15search0turn15search3

Для **4i7 я выбираю Axum**, но не потому, что Actix «плохой».

| | Axum | Actix Web |
|---|---|---|
| Модель | Tokio + Tower | Actix ecosystem |
| Middleware | Tower/Tower HTTP | собственная service/middleware модель |
| Явность | очень высокая | высокая |
| Для небольшого modular monolith | отлично | отлично |
| Интеграция с другими Tower-сервисами | особенно удобная | меньше смысла |
| Мой выбор для 4i7 | **да** | допустимая альтернатива |

Ваш проект уже строится на идее явных adapters/application/domain/infrastructure. Поэтому минималистичность Axum здесь хорошо совпадает с архитектурой.

### PostgreSQL: SQLx или Diesel

Я бы выбрал **SQLx 0.9.0**. Это async SQL toolkit с PostgreSQL/MySQL/SQLite и поддержкой compile-time checked queries без собственного SQL DSL. Версия 0.9.0 вышла 6 мая 2026 года; после неё проект переехал в организацию `transact-rs`, отражая коллективное сопровождение основными авторами. citeturn8search3turn8search1

**Diesel 2.3.x** остаётся зрелым ORM/query-builder и поддерживает PostgreSQL; он особенно хорош, когда команда хочет выражать большую часть запросов через типизированный query DSL. citeturn15search29turn15search14

Но в 4i7 уже имеют большое значение:

- явные транзакции;
- row locking/version checks;
- receipts/CAS;
- outbox;
- replay data;
- точное понимание того, какой SQL выполняется.

Поэтому здесь raw SQL + SQLx выглядит естественнее ORM. Это архитектурная рекомендация, а не утверждение, что SQLx «лучше Diesel вообще».

### Сериализация, HTTP, telemetry и API contract

**Serde 1.0.229** остаётся стандартной основой сериализации Rust data structures и форматов вроде JSON. citeturn14search0turn14search17

Для диагностики я бы использовал **tracing 0.1.44** плюс `tower-http::TraceLayer`. В async-программах structured spans особенно полезны, поскольку множество задач выполняются на одних runtime threads и традиционные независимые log lines быстро теряют причинный контекст. citeturn14search21turn10search38

Для исходящих Bot API/HTTP запросов — **reqwest 0.13.5**; он поддерживает async client, JSON и rustls. citeturn18search6

Для формального API можно использовать **utoipa 6.0.0** с `utoipa-axum`: он генерирует OpenAPI из Rust REST API и интегрируется с Axum. citeturn17search17turn17search24

Если frontend постепенно будет переводиться на TypeScript, **ts-rs 12.0.1** может генерировать TypeScript bindings из Rust types. Это особенно интересно для command/result DTO, чтобы не заводить третью ручную копию schema. citeturn17search22

### WebSocket

Axum уже имеет собственный WebSocket extractor/API через feature `ws`; отдельный transport при обычном сервере не обязателен. Для более низкоуровневого использования существует актуальный **tokio-tungstenite 0.30.0**. citeturn18search0turn18search3turn18search14

Но для **текущей 4i7 я не вводил бы WebSocket только потому, что это игра**.

Судя по текущей архитектуре, приложение уже имеет HTTP/PG path, reconnect, receipts/CAS и server-authoritative state. Issue #10 фиксирует полноценный Mini App flow, а #12 отдельно проверяет concurrency/rollback/replay guards. fileciteturn10file0L4-L7 fileciteturn11file0L4-L7

Для пошагового боя HTTP command API + периодический state refresh/long polling вполне может оказаться проще. WebSocket стоит добавлять, когда появится конкретная UX-причина: немедленный push действий соперника, spectator stream, live events и тому подобное.

## Игровое ядро 4i7: где Rust даст максимальный эффект

### Ваш проект уже устроен почти так, как я бы проектировал Rust-версию

В текущем репозитории есть отдельные `backend/domain`, `application`, `adapters`, `infrastructure`, а архитектурный документ прямо описывает modular monolith: интерфейс принимает intent, application проверяет права/версию/согласованность, pure core считает, PostgreSQL атомарно хранит результат, после commit выполняется доставка. Domain не должен зависеть от Telegram, FastAPI или ORM. fileciteturn4file0L2-L2 fileciteturn5file0L2-L2

Это очень хорошая архитектура и **её не надо ломать ради Rust**.

Самое показательное место — существующий `resolve_round()`:

```python
def resolve_round(data: t.RoundInput) -> t.RoundResult:
    ...
```

Функция валидирует input, фиксирует round-start HP, считает обе атаки относительно одного immutable начала раунда, после чего совместно применяет потери и определяет `DOUBLE_KO_DRAW`, `KO`, решение по round limit либо `CONTINUE`. Код специально подчёркивает отсутствие side effects и мутации внешнего состояния. fileciteturn9file0L2-L2

**Это почти идеальный первый кусок проекта для переноса на Rust.**

### Как я бы оформил Rust combat core

Примерная структура:

Критическое правило:

```text
combat-core dependencies
    ↓

НЕ:
tokio
axum
sqlx
telegram
reqwest

```

То есть PyO3 зависит от `combat-core`, но `combat-core` никогда не зависит от PyO3.

### Числа и детерминизм

Ваша numeric/RNG документация — один из самых сильных аргументов в пользу Rust. Сейчас контракт требует integer/basis-point probabilities, точных rational multipliers, отсутствия binary float, чётко определённого rounding и стабильного `RandomPacket`; RNG строится из серверной entropy и HMAC-SHA256 с контекстной адресацией, а replay должен воспроизводиться независимо от порядка RNG calls. fileciteturn6file0L2-L2

Я бы перенёс эти правила буквально, а не «переизобрёл их по-Rust'овски».

Например:

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct BasisPoints(u16);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct Hp(u32);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct RoundNo(u16);

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct Distance(i32);
```

Для множителя `1.27` лучше мыслить не как `f64`, а как:

```text
127 / 100
```

А затем формально определить промежуточную ширину integers, overflow policy и единственную точку округления.

`num-rational 0.4.2` предоставляет generic `Ratio<T>` и arbitrary-precision `BigRational`, но его последний текущий релиз датируется 2024 годом. Это вполне пригодный reference/test dependency, однако для канонического игрового wire/replay contract я бы предпочёл небольшой собственный bounded value type с явно документированными знаменателями и overflow rules. citeturn14search1turn14search7

Для существующего RNG доступны актуальные RustCrypto **hmac 0.13.0** и **sha2 0.11.0**. Главное — сохранить существующий алгоритм и контекстные строки/байты, а не менять RNG просто потому, что в Rust есть удобный `rand`. citeturn14search10turn14search5

То есть:

> Python replay 2026 → Rust replay 2026 должен давать тот же канонический результат.

Если этого нет — Rust migration ещё не готова.

### Дистанция, темп, движения и гранаты

Текущий DT-001 уже делает модель значительно сложнее простого «игрок A ударил B». Issue #12 фиксирует event-based distance, проверку дальности в момент действия, изменение позиций внутри раунда, joint HP application, отдельное grenade action, ordered ADVANCE/RETREAT attempts, HOLD, direction profiles, replay и concurrency checks. fileciteturn11file0L4-L7

На Rust я не стал бы превращать это в огромную mutable `Battle` class.

Лучше модель событий:

```rust
enum Action {
    Hold,
    Advance(AdvanceInput),
    Retreat(RetreatInput),
    Attack(AttackInput),
    Grenade(GrenadeInput),
}

struct ScheduledAction {
    at: Tick,
    actor: PlayerId,
    action: Action,
}
```

Затем:

```text
RoundInput
  ↓
validation
  ↓
schedule
  ↓
geometry/contact/range
  ↓
attack/grenade resolution
  ↓
joint state application
  ↓
RoundResult + Trace
```

При этом trace должен быть **результатом вычисления**, а не отладочными логами. Тогда replay, аудит спорного боя и golden tests получаются из одного и того же domain result.

### ECS или обычный domain model

Для 4i7 я **не рекомендую начинать с Bevy ECS или другого game ECS**.

ECS полезен там, где имеются тысячи heterogeneous entities/components и множество систем, проходящих по ним каждый tick. Ваш серверный бой сейчас ближе к:

> versioned deterministic rules engine + state machine + event schedule.

Для него enums, structs, pure transformations и typed value objects прозрачнее и легче тестируются.

ECS имеет смысл пересмотреть только если 4i7 когда-нибудь превратится в существенно более крупную real-time simulation model.

## Тестирование, CI, безопасность и профессиональный workflow

### Для игрового Rust обычных unit tests недостаточно

В Rust-версии 4i7 я бы делал пять уровней проверки.

**Golden tests.** Из текущей Python-реализации выгружается корпус `RoundInput → canonical RoundResult`. Rust обязан пройти его на 100%.

**Cross-language differential tests.** Генерируем input, запускаем Python engine и Rust engine, сравниваем результат.

**Property-based tests.** `proptest` генерирует большое пространство корректных и пограничных inputs и умеет shrinking — минимизирует найденный failing case. Проект продолжал обновляться в 2026 году. citeturn10search2turn10search17

В вашем случае свойства особенно очевидны:

```text
hp_after >= 0
damage_applied <= hp_before
0 <= probability_bp <= 10_000
player ordering не меняет semantic result
одинаковый RandomPacket => одинаковый result
replay(serialized input) == original result
DOUBLE_KO симметричен
```

Именно такие классы property/golden tests уже предусмотрены вашим numeric/RNG contract. fileciteturn6file0L2-L2

**Fuzzing.** `cargo-fuzz` стоит применять к codecs, JSON/binary boundaries и replay parser, особенно там, где внешние inputs могут быть повреждены; официальный rust-fuzz проект продолжал выпускать обновления в 2026 году. citeturn10search25turn10search31

**Integration tests с PostgreSQL.** Отдельно проверяются CAS/version race, две одновременные команды, rollback, idempotency receipt, outbox и reconnect.

### Test runner и coverage

`cargo-nextest` — современный test runner для Rust; текущая ветка в октябре 2026 уже находится около 0.9.148 и продолжает активно обновляться. citeturn8search23

`cargo-llvm-cov 0.8.7` даёт line/region coverage и умеет работать вместе с cargo-nextest. citeturn9search6turn9search13

Базовый CI я бы сделал примерно таким:

```bash
cargo fmt --check

cargo clippy \
  --workspace \
  --all-targets \
  --all-features \
  -- -D warnings

cargo nextest run --workspace

cargo test --doc --workspace

cargo llvm-cov nextest \
  --workspace \
  --lcov \
  --output-path lcov.info

cargo audit
cargo deny check
```

Clippy предназначен именно для выявления ошибок, подозрительных конструкций, performance/style/complexity issues; nextest, llvm-cov, RustSec `cargo-audit` и `cargo-deny` покрывают соответственно execution, coverage и dependency security/policy. citeturn16search4turn8search23turn9search13turn9search2turn9search0

### Dependency security в 2026 нельзя считать второстепенной

В 2026 Rust Project публиковал security advisories для Cargo, а также сообщал о supply-chain attack на crate `arrayref`; это хороший практический аргумент не считать Cargo ecosystem автоматически доверенным только потому, что язык memory-safe. citeturn7search11

`cargo-audit` проверяет `Cargo.lock` против RustSec Advisory Database. `cargo-deny` дополнительно умеет контролировать advisories, лицензии, запрещённые/дублирующиеся dependencies и разрешённые источники packages. Актуальные найденные версии — `cargo-audit 0.22.2` и `cargo-deny 0.20.2`. citeturn9search7turn9search9

Для 4i7 я бы запретил агентам добавлять новый crate без:

```text
1. зачем он нужен;
2. официальный repository/docs.rs;
3. дата последнего релиза;
4. transitive dependency cost;
5. cargo audit / cargo deny;
6. проверка, нельзя ли сделать задачу std/existing dependency.
```

Это особенно полезно против типичной AI-привычки добавлять crate ради пяти строк кода.

### Unsafe

Для `combat-core` я бы всерьёз рассмотрел:

```rust
#![forbid(unsafe_code)]
```

Пока нет доказанной необходимости, domain logic вообще не нужен `unsafe`.

Если `unsafe` когда-нибудь появляется в низкоуровневом коде или FFI, Miri предназначен для обнаружения undefined behavior в Rust programs и становится дополнительной проверкой. citeturn10search29

## Rust, Codex, Agent Skills и MCP

### У вас уже есть хорошая основа — но AGENTS.md пора почистить

В корне 4i7 уже существует `AGENTS.md`, в котором записаны действительно ценные инварианты: domain не зависит от Telegram/ORM/HTTP, боевая математика не копируется во frontend или handlers, разные типы изменений получают разные versions, historic battles не переводятся молча на latest, внешние side effects выполняются после commit. fileciteturn13file0L2-L2

Но там же сохранилось старое утверждение, что Mini App — кабинет, а PvP-бой проходит в личке бота. Текущий issue #10, напротив, фиксирует настоящий бой **целиком в Mini App** и отсутствие второго боевого интерфейса. Сам `AGENTS.md` говорит, что более новое решение владельца должно перекрывать старое. fileciteturn13file0L2-L2 fileciteturn10file0L4-L7

Это важнее, чем кажется.

**Сейчас у coding agent есть конфликтующий global context.**

До серьёзного Rust-развития я бы:

1. сократил root `AGENTS.md` до действительно глобальных и актуальных invariants;
2. старые исторические ограничения перенёс в отдельные reference docs;
3. Rust-специфику не раздувал бы в root AGENTS, а вынес в Skills и локальные instructions.

Это полностью совпадает с нынешней рекомендацией OpenAI: в 2026 для более сильных coding agents следует регулярно удалять из `AGENTS.md` устаревший scaffolding и избегать раздутого глобального контекста. citeturn11search12turn12search25

### Что такое Skills сейчас

Agent Skills к 2026 году оформлены как открытый filesystem-based стандарт. Минимальная skill — директория с `SKILL.md`; в ней имеются metadata и инструкции, а рядом могут лежать `scripts/`, `references/`, assets и другие ресурсы. Ключевой принцип — **progressive disclosure**: сначала агент знает только name/description, полный `SKILL.md` загружается при активации skill, дополнительные материалы — только по необходимости. citeturn12search0turn12search15

OpenAI использует ту же концепцию: skills — repeatable workflows с `SKILL.md`, references, scripts и templates; MCP и Skills решают разные задачи — **MCP даёт информацию/действия, Skill объясняет рабочий процесс и порядок использования инструментов**. citeturn11search13turn12search29

Это для 4i7 намного полезнее, чем один `AGENTS.md` на десятки страниц.

`rust-domain-core` должен сообщать агенту примерно следующее:

### Codex и локальные instructions

Codex автоматически обнаруживает `AGENTS.md` и применяет более специфичные repository/directory instructions в зависимости от расположения изменяемого файла. citeturn12search19

Поэтому разумная структура:

```text

rust/crates/combat-core/
└── AGENTS.md                   # супер-критические combat invariants
```

Например `combat-core/AGENTS.md` может содержать всего несколько правил:

```text
No floats.
No IO.
No async.
No DB.
No Telegram.
No unversioned rules.
Every semantic change needs golden/replay tests.
```

Это куда эффективнее, чем повторять всю историю 4i7 каждому агенту.

### MCP и Rust

К 2026 существует **официальный Rust SDK для Model Context Protocol — `rmcp`**. Актуальный найденный release — **3.4.0 от 15 сентября 2026 года**; SDK поддерживает server/client functionality, tools/resources/prompts и несколько transports. citeturn11search0turn11search9

Но тут я бы не впадал в «MCP ради MCP».

Для написания Rust-кода агенту прежде всего нужны:

```text
repository
cargo check
cargo test/nextest
clippy
rustfmt
rust-analyzer
canonical docs
```

MCP имеет смысл, когда нужно дать ему **живой контролируемый источник/действие**.

Например:

```text
GitHub MCP/connector
    → issues, PRs, review state

Internal 4i7 read-only MCP
    → active ruleset
    → canonical decision
    → release manifest
    → traceability lookup

Documentation MCP
    → external docs/search
```

Сам OpenAI предоставляет Docs MCP для своей документации и прямо рекомендует указывать в `AGENTS.md`, когда Codex должен им пользоваться. citeturn11search14

Я бы **не давал Rust-agent произвольный write MCP в production PostgreSQL**.

Для собственного 4i7 MCP, если он когда-нибудь понадобится, `rmcp` уже позволяет сделать сервер на Rust. Однако SDK в 2026 быстро развивался и имел несколько high-severity security advisories вокруг HTTP/OAuth/session/redirect/DNS-rebinding поведения; поэтому MCP endpoint требует обычной серьёзной threat model, обновлений и минимальных permissions. citeturn11search6turn11search9

Иными словами:

> **Skill хранит знание и workflow. MCP предоставляет capability. Не превращать знания о правилах боя в необязательный сетевой MCP, если достаточно version-controlled Markdown.**

## Telegram, TypeScript, Python и WebAssembly

### Telegram Mini App не требует Rust во frontend

Telegram Mini App остаётся HTML5/web application. Официальная Telegram документация прямо описывает JavaScript API `window.Telegram.WebApp`. `initData` следует передавать backend и проверять там; `initDataUnsafe` доверять нельзя. citeturn13search0

Telegram описывает server-side проверку `initData` через HMAC-SHA-256 и дополнительно рекомендует проверять `auth_date`, чтобы не принимать устаревшие authentication data. citeturn13search2

Это хорошо ложится на Rust:

```text
Telegram WebView
      │
      │ initData
      ▼
Axum adapter
      │
      ├─ validate Telegram HMAC
      ├─ freshness/session checks
      ▼
Application command
      ▼
combat-core
      ▼
PostgreSQL transaction
```

Telegram-specific authentication code должен жить в adapter/auth crate, **не в combat-core**.

### Что делать с текущим frontend

В просмотренной текущей ветке `frontend/` фактически содержит JS/HTML/CSS файлы вроде `api.js`, `app.js`, `cabinet.js`, `index.html`; то есть упоминаемый в архитектурных предложениях TypeScript/React/Vite не следует путать с тем, что прямо сейчас лежит в основной frontend-части репозитория. fileciteturn12file0L1-L2

Я бы не связывал внедрение Rust с обязательным переписыванием frontend.

Порядок лучше такой:

```text
сначала Rust combat-core
        ↓
потом TS contracts
        ↓
потом, при необходимости, modernized frontend
```

Frontend не должен считать альтернативную боевую математику — это уже одно из требований вашего проекта. fileciteturn13file0L2-L2

### Где действительно полезен WebAssembly

Актуальный `wasm-bindgen` на момент проверки — **0.2.129**, релиз 25 сентября 2026 года; он предоставляет bindings между Rust/Wasm и JavaScript. citeturn15search5

В 4i7 WASM становится интересным **после того, как `combat-core` уже стабилен на сервере**.

Тогда тот же core можно потенциально собрать:

```text
combat-core
   ├─ native Rust → production server
   └─ wasm32      → browser replay/sandbox/preview
```

И это даёт очень сильную модель:

> одна математика → два targets.

Но WASM-версия в клиенте никогда не должна становиться authority. Игрок может модифицировать browser runtime. Она подходит для replay, визуального preview, research/sandbox, локального расчёта UI hints — сервер всё равно пересчитывает и принимает результат самостоятельно.

### Как интегрировать Rust с существующим Python

Здесь появляется особенно хороший вариант — **PyO3 + maturin**.

Актуальный PyO3 — **0.29.3 от 30 сентября 2026 года**; он позволяет писать native Python modules на Rust. Maturin предназначен для сборки и упаковки Rust/PyO3 modules как Python packages/wheels. citeturn19search7turn19search5

То есть текущий backend сможет делать концептуально:

```python
from combat_rust import resolve_round

result = resolve_round(round_input)
```

А внутри работает Rust.

Это означает:

```text
Telegram adapter     Python — остаётся
Application layer    Python — остаётся
PostgreSQL            Python — остаётся
Workers               Python — остаются

Combat core           Rust — новый
```

С точки зрения риска это, на мой взгляд, **самая сильная схема миграции 4i7**.

Нет:

- второго HTTP service;
- нового network hop;
- нового deployment unit;
- распределённой транзакции;
- необходимости сразу переписывать backend.

И при этом появляется реальный production Rust.

## Практический план для 4i7 и итоговый стек

### Что я обнаружил в самом проекте

4i7 уже далеко не «маленький Telegram-бот». Репозиторий разделён на backend/domain/application/infrastructure/adapters, frontend, docs, migrations, tests и rulesets; документация предусматривает versioned combat engine, replay и manifest. fileciteturn1file0L2-L2 fileciteturn5file0L2-L2

Live-направление уже перешло к полноценному бою внутри Mini App, а текущая distance/tempo работа включает event schedule, range/contact, движения и гранату с server-side validation и replay guarantees. fileciteturn10file0L4-L7 fileciteturn11file0L4-L7

Поэтому у вас **нет проблемы «Python слишком медленный, срочно переписываем»**. Главная ценность Rust здесь другая:

> сделать растущее rule engine типобезопаснее, воспроизводимее, легче для формальной проверки и безопаснее для будущих изменений.

### Лучший путь внедрения

#### Сначала — shadow Rust core

Создать:

```text
rust/crates/combat-contract
rust/crates/combat-core
```

Без production integration.

Из существующего Python engine экспортировать golden corpus:

```json
{
  "input": { "...": "..." },
  "expected": { "...": "..." }
}
```

Rust engine должен пройти все vectors.

Особое внимание:

```text
rounding
basis points
overkill
double KO
player order
range/contact
movement ordering
grenade
RNG context bytes
serialization
manifest version
```

Это соответствует уже формализованным требованиям numeric/replay в репозитории. fileciteturn6file0L2-L2

#### Затем — differential testing

Один test harness:

```text
generated input
      ├── Python → result A
      └── Rust   → result B
                    ↓
                compare
```

Не «примерно одинаковый», а либо semantic equality, либо canonical byte equality там, где wire contract этого требует.

Пока эта стадия не зелёная, production вообще не трогаем.

#### Затем — PyO3 boundary

После parity Rust engine подключается в Python backend через PyO3/maturin. PyO3 именно для этого предоставляет native Python extension mechanism. citeturn19search1turn19search7

Первоначально можно сделать default-off/shadow mode:

```text
Python authoritative engine
Rust shadow engine
        ↓
compare
        ↓
metrics
```

И только после достаточного корпуса реальных/fixture matches поменять authority.

#### Только потом — решение о Rust backend

После нескольких релизов станет понятно, нужен ли перенос:

```text
application
API
DB
worker
Telegram
```

Если Python transport/backend остаётся удобным и производительность устраивает — **его можно вообще не переносить**.

Это совершенно нормальная конечная архитектура.

Если же вы решите строить следующую большую игру уже преимущественно на Rust, тогда существующий combat-core просто переезжает в:

```text
Axum
  ↓
application
  ↓
combat-core
  ↓
SQLx/PostgreSQL
```

### Три варианта стратегии

| Стратегия | Риск | Мой вердикт |
|---|---:|---|

### Как я бы изучал Rust именно через ваши задачи

Не стал бы несколько месяцев сначала «учить весь Rust».

**Первый учебный проект:** небольшая библиотека точной arithmetic 4i7. `BasisPoints`, rational multiplier, rounding, HP calculation. Никакого async.
